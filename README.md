# UDP 多端口并发探测 + 隧道转发系统

## 一、系统原理

### 1.1 整体架构

```
┌─────────────┐    UDP随机端口探测     ┌─────────────┐
│   客户端A   │ ──────────────────> │             │
│  (本机)     │ <────────────────── │   服务端    │
└─────────────┘    隧道建立后双向转发  │  (远端)     │
                                      │             │
┌─────────────┐    UDP随机端口探测     │             │
│   客户端B   │ ──────────────────> │             │
│  (本机)     │ <────────────────── │             │
└─────────────┘    隧道建立后双向转发  └─────────────┘
```

### 1.2 核心流程

#### 阶段一：端口探测（随机打孔）

1. **端口池初始化**：使用 Fisher-Yates 洗牌算法将 1-65535 端口随机打乱
2. **批量发送**：管理器线程从打乱的数组中顺序取出端口（相当于随机），每个端口创建独立的 `DatagramSocket`
3. **并发探测**：每个端口同时运行发包线程和收包线程，向目标主机发送 `PING` 数据包
4. **响应检测**：任意端口收到响应后，立即标记隧道建立，关闭其他端口

```
端口池: [48355, 33020, 29894, 51416, 288, ...]  ← 打乱后的随机顺序
         │
         ▼ 顺序取出 = 随机选取
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │端口48355│  │端口33020│  │端口29894│  ... (最多3000个并发)
    │PING →   │  │PING →   │  │PING →   │
    │← 响应?  │  │← 响应?  │  │← 响应?  │
    └─────────┘  └─────────┘  └─────────┘
         │
         ▼ 某个端口收到响应
    ═══════════════════════════
    隧道建立，保留该 socket
    关闭其他所有端口
    ═══════════════════════════
```

#### 阶段二：隧道转发

隧道建立后，程序启动三个守护线程：

| 线程 | 功能 | 数据流向 |
|------|------|----------|
| `LocalToTunnel` | 监听本地端口，转发到远端 | 本地客户端 → 隧道 → 远端服务器 |
| `TunnelToLocal` | 监听隧道返回，回传给本地客户端 | 远端服务器 → 隧道 → 本地客户端 |
| `KeepAlive` | 定期发送心跳包维持连接 | 隧道 → 远端（每30秒） |

### 1.3 关键数据结构

| 数据结构 | 类型 | 作用 |
|----------|------|------|
| `shuffledPorts` | `int[65535]` | 打乱的端口数组，O(1)随机选取 |
| `shuffleIndex` | `AtomicInteger` | 当前取到数组的哪个位置 |
| `returnedPorts` | `Set<Integer>` | 归还的端口，优先从这里取 |
| `activeQueue` | `LinkedBlockingDeque` | FIFO活跃队列，控制并发数 |
| `TUNNEL_SOCKET` | `AtomicReference<DatagramSocket>` | 隧道建立后的活动socket |
| `TUNNEL_REMOTE` | `AtomicReference<InetSocketAddress>` | 远端响应地址 |
| `CLIENT_MAP` | `ConcurrentHashMap` | 已连接的本地客户端地址 |

### 1.4 可配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `TARGET_HOST` | `113.4.45.38` | 目标主机 IP |
| `RATE_PER_SECOND` | `100` | 每个端口每秒发包数 |
| `LOCAL_LISTEN_PORT` | `9999` | 本地 UDP 监听端口 |
| `QUEUE_SIZE` | `3000` | 活跃端口队列最大长度 |
| `PORT_ADD_INTERVAL_MS` | `10` | 每次添加端口的间隔（毫秒） |
| `KEEPALIVE_INTERVAL_MS` | `30000` | 心跳间隔（毫秒） |

### 2.4 连接速度参考

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 端口池初始化 | ~50ms | Fisher-Yates 洗牌65535个端口 |
| 填满3000端口队列 | ~30秒 | 每10ms添加一个端口 |
| 隧道建立 | 取决于远端响应速度 | 收到第一个响应即建立 |
| 数据转发延迟 | <1ms | UDP 直接转发，无 TCP 握手 |
| 心跳间隔 | 30秒 | 可配置 |

**总连接建立时间估算：**
- 本地启动到开始发包：~30秒（填满队列）
- 首次收到响应：取决于网络延迟和远端响应速度
- 隧道建立后：立即可用，转发延迟 <1ms

### 2.5 连接成功概率算法

当双方以相同速度 `n`（包/秒）同时向对方发包时，隧道建立的概率如下：

#### 数学模型

假设：
- 端口总数：`M = 65535`
- 每秒发包数：`n = RATE_PER_SECOND`
- 双方速度相同

**失败概率**（所有包都不碰撞）：

```
P(失败) = ∏(i=1 → n) (M-i)/M
        = (65534/65535) × (65533/65535) × ... × ((65535-n)/65535)
```

**成功概率**（至少有一个碰撞）：

```
P(成功) = 1 - P(失败)
        = 1 - ∏(i=1 → n) (65535-i)/65535
```

#### 计算示例

| 每秒发包数 (n) | 失败概率 P(失败) | 成功概率 P(成功) | 说明 |
|---------------|-----------------|-----------------|------|
| 1 | 65534/65535 ≈ 99.998% | ≈ 0.002% | 极慢，几乎不可能 |
| 10 | ≈ 99.93% | ≈ 0.07% | 很慢 |
| 50 | ≈ 98.15% | ≈ 1.85% | 慢 |
| 100 | ≈ 92.59% | ≈ 7.41% | 当前默认值 |
| 200 | ≈ 73.96% | ≈ 26.04% | 较快 |
| 500 | ≈ 21.30% | ≈ 78.70% | 快 |
| 1000 | ≈ 0.30% | ≈ 99.70% | 极快 |

#### 近似公式

当 `n << M` 时，可用近似公式快速估算：

```
P(失败) ≈ e^(-n²/(2M))
P(成功) ≈ 1 - e^(-n²/(2M))
```

例如 `n=100`：
```
P(失败) ≈ e^(-100²/(2×65535)) ≈ e^(-0.0763) ≈ 92.66%
P(成功) ≈ 1 - 0.9266 ≈ 7.34%
```

#### 优化策略

1. **提高发包速率**：`RATE_PER_SECOND` 从100提高到500，成功率从7%提升到79%
2. **多端口并发**：同时使用多个端口发包，相当于增加 `n`
3. **持续探测**：即使单次失败，持续发包会累积成功概率

#### 累积成功概率

如果持续探测 `t` 秒，每秒成功概率为 `p`，则：

```
P(至少一次成功) = 1 - (1-p)^t
```

例如 `n=100`（p≈7.4%），持续探测：
| 探测时间 | 累积成功概率 |
|---------|-------------|
| 1秒 | 7.4% |
| 5秒 | 32.3% |
| 10秒 | 53.3% |
| 30秒 | 89.3% |
| 60秒 | 98.9% |
| 120秒 | 99.97% |

## 三、常见问题

### Q1: 为什么浏览器无法访问 http://127.0.0.1:9999 ？

**A:** 9999 端口监听的是 **UDP** 协议，浏览器发送的是 **HTTP/TCP** 请求，两者不兼容。需要使用 UDP 客户端（如 `SendPageack`）或 `nc -u` 命令测试。

```bash
# 使用 netcat 发送 UDP 数据
echo "Hello" | nc -u 127.0.0.1 9999
```

### Q2: 对方收到数据后需要转换吗？

**A:** 取决于对方服务器类型：
- 如果对方是 **UDP 服务器**：直接收到原始 UDP 数据，无需转换
- 如果对方是 **HTTP/TCP 服务器**：需要在对方部署 UDP→TCP 转换程序

### Q3: 心跳包的作用是什么？

**A:** UDP 是无连接协议，没有 TCP 的 keepalive 机制。心跳包的作用：
1. 维持 NAT 映射不被清除
2. 检测隧道连接是否仍然有效
3. 防止中间网络设备因超时关闭连接

### Q4: 队列满了会怎样？

**A:** 当活跃队列达到 `QUEUE_SIZE`（默认3000）时，管理器会：
1. 从队列头部取出最老的连接
2. 关闭该连接的 socket
3. 将端口号归还到可用池
4. 新端口可以继续加入

这实现了端口的循环利用，确保系统可以持续运行。
